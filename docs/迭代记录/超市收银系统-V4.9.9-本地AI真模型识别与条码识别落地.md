## 三、排错实录（端到端为何一直降级 dHash）

修复链路中共定位并解决 6 个问题，其中第 4 个是**最核心的隐蔽根因**：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 识别请求直接 400/无效 | 设置项 `ai.ocr.vl_model='qwen2.5-vl:7b'` 是不存在的模型；`ai.llm.enabled=false` | 改为 `qwen2.5vl:3b`；`ai.llm.enabled=true` |
| 2 | 知识库查询报错 | `SELECT DISTINCT ... ORDER BY s.id` 触发 PG 报错（DISTINCT 的 ORDER BY 列必须在 select list） | 改为 `ORDER BY s.product_id DESC` |
| 3 | 设置 UPDATE 报 `invalid input syntax for type json` | `system_settings.value` 是 JSONB | 写入带引号标量 `'"vl"'` |
| 4 | **Ollama 直接调通，但走路由必降级 dHash（6.3s 延迟证明模型确实被调用）** | **Ollama 默认 `num_ctx=4096`。多图请求（实时帧+参考图）预处理后 4212 tokens 溢出，Ollama 返回 HTTP 400 `exceed_context_size_error`。旧代码只抛 `Ollama HTTP 400` 不带错误体，路由 catch 后静默降级 dHash，表象完全像"模型没接上"** | 三重修复：① `downscaleB64()`（jimp 等比缩放最长边 ≤640px + JPEG 重编码）压视觉 token；② 请求显式 `options.num_ctx=16384`；③ `callVL` 失败时透出 Ollama 错误体前 300 字符，降级日志可定位 |
| 5 | 编译报 TS2616 | jimp 0.22 CJS 类型不支持命名导入 | `import Jimp from 'jimp'`（tsconfig esModuleInterop=true 下运行时经 interop 包装正确拿到 Jimp 类） |
| 6 | 端口占用 + 重启后行为异常 | 累积 9 个 `dist/main.js` 僵尸进程 | 全部清理后单实例重启 |

**方法论沉淀**：`usedFallback=true` 且延迟数秒 = 模型真的被调用了但抛了异常。先用"直接调用编译后函数 + JWT 解码真实 storeId"复现，再看 Ollama 错误体——400 大概率是 `num_ctx` 溢出，而不是"模型不可用"。

## 五A、追补修复：实机扫码"基本扫不出"根因排查（2026-09-08 上午）

用户反馈：手机端通过"扫码"识别一维码条码基本没有成功过（银豹手机端可秒扫）。经无头浏览器 + 相机仿真实验逐层定位，**真凶不是一个，是叠加的三层**：

### 根因 1（致命）：ZX_FORMATS 用了非法枚举名 → wasm 返回空文本伪命中

`zxing-wasm v3.1.3` 的合法格式枚举名是 `EAN-13`/`UPC-A`/`QRCode`/`DataMatrix`/`PDF417` 风格（`share.js` 别名表核实），原代码写的 `QRCODE`/`DATA_MATRIX`/`PDF_417`/`RSS_14` 均为**非法名**。实测后果：列表一旦混入非法名，wasm 解码返回**text 为空串的伪命中**（`len=1 [{"text":""}]`），被前端空文本过滤后变成空数组——**表象就是"永远扫不出"**，且无任何报错。

修复：`ZX_FORMATS` 改为 15 项合法枚举名（EAN-13/EAN-8/UPC-A/UPC-E/Code128/Code39/Code93/Codabar/ITF/QRCode/MicroQRCode/DataMatrix/Aztec/PDF417/DataBar），并在回归脚本中静态校验该列表全为合法名，防再犯。

### 根因 2：ROI 趟返回值 bug → zxing 通道在浏览器里从未真正跑通

`roiScaled` 返回的是 pool 包装对象 `{cv,ctx,w,h}`，而 `readBarcodes` 对该形态抛 `Invalid input type`（仅接受 ImageData 或 `{data,width,height}` 纯对象）。修复：ROI 趟返回 canvas；`detectZX` 入参统一归一化为 `{data,width,height}`。**此 bug 意味着旧版在无 BarcodeDetector 的环境（iPhone Safari/微信内核）里 zxing 兜底等于不存在**——与"基本没成功过"完全吻合。

### 根因 3：扫描策略弱（光学层面）

相机仿真实验（1280×720 场景合成不同画幅/模糊度条码）结论：
- 清晰图上 17% 画幅的小码全帧即可解出——纯算法不是瓶颈；
- **blur≥1px 小码即死**，实机"凑近能扫、稍远就废"的主因是失焦模糊；
- 最近邻放大反而劣化，ROI 放大必须双线性。

### 扫描管线 V2（多趟解码 + 硬件能力全开）

`barcode-decode.js` 重写为扫描级多趟管线（帧内短路，任一趟命中即返回）：

| 趟 | 内容 | 目的 |
|---|---|---|
| T1 | 原生 BarcodeDetector 全帧 | Android Chrome 快路径 |
| T2 | 中央 40% 高 ROI 带（zxing） | 排除背景干扰，聚焦条码区 |
| T3 | ROI 双线性放大 ×2 | 小码增强 |
| T4 | 中央 30% 小窗放大 ×3 | 远距/极小码 |
| T5 | 全帧 zxing tryHarder 兜底 | 条码在画面边缘的场景 |

配套复用池（canvas/ImageData 单例，杜绝每帧分配）、`willReadFrequently`、统计面板 `BarcodeDecode.stats`（frames/hits/lastMs/lastEngine）。`work.js` Scanner 升级：1080p 流 + 数码变焦滑杆（zoom 能力检测，**小码/远距识别率关键**）+ 连续自动对焦 + 点击对焦 + 手电筒 + 实时状态行（让"扫不上"可被看见可报告）。

## 六、已知边界与后续建议

1. **近似商品混淆（模型精度，非工程问题）**：宜简纯净水的样本帧同时命中了"PWA矿泉水700943"（conf 均 0.9）——两个都是透明瓶装水，3B 少样本定位下可理解。缓解手段：同商品多张参考图、提高 `ai.fallback_conf`、或后续换 7B 视觉模型（需先 `ollama pull`）。
2. **冷启动延迟**：首次识别含模型加载约 28s，暖态 3s。生产建议 Ollama 常驻 + `keep_alive` 保活。
3. **浏览器摄像头实机验证**：逻辑层已在无头 Chromium（无 BarcodeDetector 环境）用相机仿真图真实验证通过；真手机摄像头（对焦/曝光/抖动）烟测仍建议做一次，扫码界面已提供状态行与变焦辅助排障。
4. **上下文预算**：当前单次最多 12 个商品参考图（`MAX_REFS`），640px 压图后 16384 ctx 余量充足；门店商品数远超 12 时需引入"候选预筛"（如先 dHash 粗排取 Top-N 再送 VL 精判）——已在设计上预留该组合路径。
