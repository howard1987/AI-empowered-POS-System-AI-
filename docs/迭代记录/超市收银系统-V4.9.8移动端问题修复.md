# 社区超市收银系统 · 移动端问题修复说明 V4.9.8

> 范围：店员端 PWA（`backend/public/pwa`）+ 老板端（`backend/public/boss`）+ 后端接口/迁移
> 背景：老板反馈移动端 4 类问题——扫码扫不出、AI 拍多件识别空、缺返回键、老板看不到报表明细且无法手机审批。
> 验证环境：本地 PG（54329）+ 后端（3100），`tests/_verify_v498_mobile.mjs` 回归 **19/19 通过**。

---

## 一、问题清单与根因

| # | 现象 | 根因 |
|---|------|------|
| 1 | 移动端扫描**识别不了商品二维码/条码** | ① 后端价目表仅下发主条码，辅助码/包装码/称重码缺失；② 前端 `lookupProduct` 只对「6~16 位纯数字」走条码接口，字母数字二维码、带 URL/前缀的码、UPC 补零码、去校验位码一律落到关键词搜索→必然扫不出 |
| 2 | AI 拍多件**识别不出商品** | 识别为真实样本 dHash 匹配，店端未采集样本的商品的识别结果恒为空，且空结果只静默失败，无引导、无兜底 |
| 3 | 部分功能模块**没有「‹」返回** | PWA 子页面返回栈在 `openTab` 时被清空；老板端无返回按钮；个别弹层（如缺货登记）无关闭入口 |
| 4 | 老板端**看不到报表明细**、**无法手机审核/驳回** | 报表页仅图表无表格；审批页仅展示待办列表，无详情/通过/驳回；后端无「驳回」类接口（仅有审核/作废） |

## 二、修复方案

### 1. 扫码识别（二维码 + 一码多品 + 称重/包装码 + 校验位回退）

**后端 `pos.module.ts` `GET /pos/pricebook`**
- 价目表额外下发 `barcodes`（主码 + `product_barcodes` 辅助码 + `product_units` 包装码），离线 Pricebook 可命中多码。
- 商品对象补齐 `barcodes` 字段，前端 `Pricebook.find` 支持按任意码命中。

**前端 `pwa/work.js`**
- 新增 `normBarcode()`：去空白/全角 → 去 AIM 前缀（`]C1` 等）→ 去 `CODE128:`/`EAN13:` 等协议前缀 → URL 取码（`?code=`/末段路径）。
- 新增 `barcodeCandidates()`：原码 → 去前导零 → EAN-13 去校验位 → UPC-A 补零成 EAN-13 → EAN-8 去校验位。
- `lookupProduct()` 重写：离线 Pricebook 优先 → 4~48 位可打印字符统一走 `/products/barcode`（逐候选回查）→ 末位关键词搜索兜底。
- 命中「一码多品」弹 `pickProductModal` 人工选择；未命中弹 `scanMiss` 给出可行动提示（换关键词/改用 AI/去建档）。
- 全部 `Scanner.attach` 回调（收货/退供/盘点/报损/拣货/AI 采集/移动收银）统一走 `scanResolve`。

**前端 `pwa/checkout.js`**：`Pricebook.find` 支持多码；`addCart(p, qty)` 支持扫码带数量；`lookupProduct` 兜底命中。

### 2. AI 拍多件识别引导

**前端 `pwa/ai-scan.js`**
- 打开识别前检测样本就绪度（`GET /ai/samples`），样本数为 0 时先提示「请先到 AI 训练采集拍 6 个角度」，不进空识别。
- 识别结果为空：明确提示「该商品尚未采集样本」+「改用扫码添加」一键跳转，连续空识别不再静默失败。
- 共享函数 `addAiFallback(aiItems, addOne)`：扫码未命中→转 AI 识别后的结果落明细。

### 3. 返回功能

- **PWA `app.js`**：返回栈 `push/pop` 改为不丢失路径，`openTab` 仅切底 tab 时清空；补 `popstate` 监听（手机系统返回键/手势回退）。
- **老板端 `index.html` + `app.js`**：新增顶部 `‹` 返回按钮（默认隐藏，进子页面显示）；`push()` 压 `history.pushState`，`hdBack.onclick` 优先 `history.back()` 再兜底 `popView()`；`popstate` 同步出栈。
- **PWA `ops2.js`**：缺货登记弹层补「‹ 返回」关闭按钮；所有弹层缺失关闭入口时由通用逻辑兜底注入。

### 4. 老板端报表明细（移动端表格）

**前端 `pwa/../boss/app.js` `View.reports` 及 `rep*` 系列**
- 营业日报（区间切换）、ABC 分类、商品销售明细（搜索+分页）、会员消费榜、进销存报表、员工业绩——共 6 张移动端表格视图，行可点击展开明细。
- 数据源均为既有后端报表接口（`/reports/*`），已验证可取。

### 5. 老板端手机审核 / 驳回

**前端 `boss/app.js`**
- `View.approve`：聚合入库/退货/报损/盘点/采购订单待办，点行进详情。
- `View.approveDetail`：展示单据头（单号/供应商/状态/金额/制单人/凭证图/签名图）+ 明细表 + 通过/驳回按钮；**驳回必填原因**（`prompt` 强制）；采购订单审批走 `signSheet` 电子签名。
- 操作成功回写列表并 `toast` 反馈；审计留痕由后端统一完成。

**后端 `purchase.module.ts` / `inventory.module.ts`（V4.9.8）**
- 新增 4 个驳回接口：`POST /purchase/inbounds/:id/reject`、`POST /purchase/returns/:id/reject`、`POST /inventory/losses/:id/reject`、`POST /inventory/counts/:id/reject`。
- 仅「未审核/草稿/待审核」可驳回→置 `已驳回`，原因入库 + `audit_logs` 留痕（`inbound.reject`/`return.reject`/`loss.reject`/`count.reject`）；已审核单不允许驳回（走退货/作废）。

**数据库 `db/040_approve_reject.sql`**
- `inbound_status_t`/`return_status_t`/`count_status_t` 扩展枚举值 `已驳回`；
- `inbound_orders`/`purchase_returns`/`inventory_counts` 增加 `reject_reason`/`rejected_by`/`rejected_at`；
- `loss_records` 增加 `reject_reason`/`rejected_by`/`rejected_at`（报损原状态枚举已含 `已驳回`）。

## 六、补充增强：银豹式红色基线取景辅助（扫码体验）

参考银豹收银：手机摄像头拍二维码时，取景框中央有一条**红色基线**，将基线对准二维码/条码即可快速对齐识别。

- `pwa/work.js` `Scanner.start`：视频外层包 `.scan-view`，叠加 `.scan-frame`（四角红色角标 + 中央静态红色基线 + 上下扫动的红色扫描线）。
- `pwa/index.html` 样式：基线色 `#ff3b30`，角标/基线 `pointer-events:none`（点击穿透到 video 仍可点击对焦）；扫描线用 CSS `@keyframes` 动画，并对 `prefers-reduced-motion` 关闭动效。
- 提示文案改为「将红色基线对准条码/二维码中心」。
- 该取景辅助覆盖 PWA 全部扫码入口（收货/退供/盘点/报损/拣货/AI采集/移动收银），因 Scanner 仅 `work.js` 一处定义。
- 视觉对齐辅助不改变解码区域（BarcodeDetector / ZXing 仍对整帧解码），纯提升用户对准速度与识别率。

## 七、识别链路根因修复（条码优先 + dHash 兜底 + 架构事实）

> 老板反馈：清晰的一维码也扫不出；"宜简饮用纯净水"已提交 12 张训练样本，AI 拍多件仍提示"匹配不上"。本次不是补丁，是识别链路的根因修复。

### 7.1 必须先说清的架构事实（重要）

**当前代码并没有部署"AI 大模型"。** 全项目无任何 Python / PyTorch / ONNX 推理服务（已全量搜索确认）。商品识别实际只有两条路径：

| 能力 | 当前实现 | 是否模型 |
|------|----------|----------|
| 条码/二维码 | 浏览器原生 `BarcodeDetector`（无则 ZXing 软解） | ❌ 不是模型，是解码器 |
| 图片商品识别 | `ai.sample-match.ts` 的 **dHash 感知哈希**比对样本库 | ❌ 不是模型，是哈希相似度 |

设计文档提到的"本地 AI 模型部署（PyTorch/ONNX）"**尚未落地**——代码里仅有 `runDetection()` 桩 + `ai_models` 表 + ONNX 路径占位，`ai.engine` 默认 `'mock'` → 实际走 dHash。所以"部署了 AI 大模型、识别应更上一层楼"的预期，与当前实现存在落差，这是本次"匹配不上"的**认知根因**。

### 7.2 为什么清晰一维码也扫不出

1. **裁剪回归（已撤销）**：上一轮为提升对准率，把检测区收窄为"画面中间 34% 条带"，要求条码必须落在红线区域。但实拍时条码常在画面底部/顶部 → 永远进不了检测区 → 扫不出。本次**恢复整帧检测**，红线仅作视觉对齐引导，不作硬性闸门。
2. 整帧 `BarcodeDetector` 对清晰一维码/二维码识别率极高，撤销裁剪后回归正常。

### 7.3 为什么 12 张样本"匹配不上"

`/ai/recognize` 的匹配是 dHash（8×8 = 64 bit 哈希）：
- dHash 对**位移 / 缩放 / 背景 / 光照**极度敏感。活体拍的一帧与训练样本角度一变，汉明距离轻松超过阈值 15，全部被丢弃。
- 更关键：**`recognize` 接口从未尝试从画面里检测条码**。而"宜简饮用纯净水"瓶身就有条码 `6950549800187`，最可靠的识别是"读条码→定位商品"，却被完全忽略。

> 说明：`/upload` 返回 `/uploads/xxx.jpg`、样本 `image_path` 也以 `/uploads/` 前缀存储、文件落盘 `public/uploads/`，**存储与查询路径均正确，12 张图确实进了样本库**——问题不在"没存进"，而在 dHash 太弱 + 没走条码。

### 7.4 修复方案（把"条码优先"作为核心能力）

**① 扫码 `pwa/work.js` `Scanner.start`**：撤销中间条带裁剪，恢复 `detector.detect(video)` 整帧检测；红线仅视觉引导。

**② AI 拍多件 `pwa/ai-scan.js`**：新增 `mergeBarcodeHits()`——
- 自动识别循环每帧先用 `BarcodeDetector` 检测画面内**所有**条码；
- 每个条码经 `lookupProduct()` 定位商品（本地 Pricebook + 后端 `/products/barcode` + 关键词兜底，归一化已含去校验位/补零/去前缀）；
- 定位到的商品以 `conf=1` 并入候选清单；
- **仅当本帧无任何条码命中时，才调用 `/ai/recognize` 走 dHash 样本兜底**。
- 效果：带码商品（绝大多数零售品）秒识别，不再依赖样本；手动"立即识别"也先试条码。
- 提示文案同步修正：带条码商品对准条码即秒识别；无条码商品才靠样本图片相似度（准确率有限）。

**③ dHash 兜底 `src/modules/ai.sample-match.ts`**（仅影响"无条码商品"）：
- `MATCH_DIST` 15 → **20**；
- 新增 **aHash**（平均哈希，抗位移）`MATCH_DIST_A = 10`；
- 匹配条件改为 **dHash ≤ 20 或 aHash ≤ 10 任一达标即命中**，显著降低无条码品的漏匹配（双哈希互补：dHash 抗亮度、aHash 抗平移）。

### 7.5 生效方式

- **前端（work.js / ai-scan.js / index.html）为静态文件**，运行中后端从磁盘逐请求读取 → **手机 PWA 硬刷新（清缓存）即生效**，无需重启。"宜简饮用纯净水"类带码商品经此路径已可识别。
- **后端（ai.sample-match.ts）需重新编译 + 重启**才生效（仅影响 dHash 兜底）：
  ```bash
  cd 超市收银系统-初版代码/backend
  node_modules/.bin/tsc -p tsconfig.json
  # 重启 3100 实例（或杀掉旧进程由 runtime-watchdog 拉起新 dist）
  ```

### 7.6 后续（真正的"AI 大模型"识别）

若要"无条码商品也能识别、一框多件同识别、角度/光照鲁棒"，需部署**真正的本地视觉模型**（YOLO 检测 + 商品 embedding 分类，或轻量多模态），由 Python 服务（FastAPI + ONNX Runtime）承载，对接现有 `runDetection()` 桩与 `ai_models` 表。这属于独立工作流，建议单独立项排期，不在本次移动端修复范围内。
