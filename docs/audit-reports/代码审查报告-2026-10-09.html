P0L-01

连锁同步失败处理 SQL 对同一列赋值两次 —— 重试 / 退避 / 死信机制从未生效过

✓ 已逐行核验
backend/src/modules/sync-store.service.ts:175-181, 187-191, 200-205 
UPDATE sync_outbox SET status='failed', last_error=$2,
   retry = retry + 1,
   next_retry_at = now() + (...),
   status = CASE WHEN retry + 1 >= $3 THEN 'dead' ELSE status END  -- status 第二次出现
 WHERE idem_key=$1
PostgreSQL 对 SET 中重复列直接报 multiple assignments to same column "status"。三处同型：被总部拒绝（rejected）的循环没有 catch → 异常冒泡使整轮 push 判失败并计入熔断；网络失败分支带 .catch(()=>{}) → 静默失败。后果：retry 永不自增、next_retry_at 永不生效、dead 死信永远落不了——永久失败的单据（如跨店撞号）每 60 秒无限重推锤总部。当前连锁同步的“失败处理”路径实际上是一条从未跑通过的死路。
修复：合并为单次赋值：SET last_error=$2, retry=retry+1, status = CASE WHEN retry+1>=$3 THEN 'dead' ELSE 'failed' END, next_retry_at = CASE WHEN retry+1>=$3 THEN NULL ELSE now()+make_interval(secs=>$4) END；并补一条针对 rejected 分支的集成测试（可用本地假 HQ 返回 rejected 验证）。

P0L-04

在数据库事务内发起真实资金指令（总部扣款 / 通道退款）—— 回滚了事务，回滚不了钱

✓ 行号经抽样核验
backend/src/modules/sales.module.ts:782, 832, 866（结账事务内 hqMemberPost）· refund.module.ts:317 → pay.gateway.ts:270-275
连锁余额/分红/积分支付在 tx() 内同步 HTTP 调总部扣款（超时 8s）：总部扣款成功后，本地任何一步失败（金额不平 :905、审计写入异常）都会 ROLLBACK——总部余额已实扣而订单不存在，只能靠 3 天后的每日 job 冲正。退款同理：通道原路退款成功后本地回滚 → 顾客已到账、系统无记录（直接资损）。叠加 L-05/P-01 的全天发号锁：一条慢 HQ 响应能阻塞所有收银台的结账；HTTP 挂起期间持续持有 member_accounts/batches 行锁，正是 db.ts 注释里记录过的“连接被抢光 → 系统错误”故障模式的重演剧本。

P0P-01

✓ 已逐行核验
backend/src/common/db.ts:76-81（seqLock）· 调用例 sales.module.ts:634 · 30+ 种单据复用 
await c.query(`SELECT pg_advisory_xact_lock(hashtext($1))`, [`seq:${table}:${pattern}`]);

单号“取号即放”被实现成“取号锁跟到事务尾”：多收银机并发时，从发号那一刻起全部结账串行排队，每单后面几百毫秒的事务体（L-04 的 HTTP、逐行扣批、审计）都乘进队头时延。同时每笔结账都对当日订单做 LIKE 前缀 count——按日均 3000 单、半年 50 万行估，单次 30–150ms 且持续恶化。这是把“防撞号”做成了“全局堵号”。（该文件此前已因连接池 10 太小导致结账排队报错过，本次修的是根因的另一半。）

P1S-01

员工停用存在 60 秒操作窗口，且吊销缓存清理只在当前进程

✓ 已核验 auth.ts:74-85,114-117
empState 60s 进程内 Map 缓存吊销判定；停用路径只调 clearAuthStateCache（本进程）且不推进 token_version。多实例（PM2 cluster）下其它 worker 的缓存在 ≤60s 内仍放行被停收银员结账/退款——离职即时冻结在单进程部署勉强够用，横向扩展后是舞弊窗口。
