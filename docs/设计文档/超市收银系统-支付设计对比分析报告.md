# 超市收银系统 · 支付设计对比分析报告

> 对照对象：《聚合支付实现设计报告 · 微信支付 × 支付宝》（payment-design.html v1.0，2026-09-09）
> 本方依据：《超市收银系统设计方案》V4.8.22 支付相关章节（5.1.16 / 5.2 / 6.4.1 / 第八章支付服务）+ 后端实际代码（sales.module.ts / finance.recon.ts）
> 日期：2026-09-09 ｜ 结论面向决策：**两份设计不是竞品，是互补关系——对方是我们尚未建设的"商户支付 API 层"施工图**

---

## 一、一句话结论

对方报告是一份**质量相当高的线上支付 API 集成设计**（验签、幂等、查单兜底、对账终审的完整闭环），但它只覆盖了"钱从微信/支付宝进来"这一条线；我们的支付设计真正的深度在**组合支付 + 会员资产账户**（储值/分红/积分服务端扣减、有效消费合规封堵、FIFO 退款原路），这是对方完全没有的维度。**对方 9 章内容中约 70% 是我们接通商户支付 API 时必须补的课，其余 30%（被扫/沙箱/部分场景）是锦上添花。**

---

## 二、定位差异（先分清比的是什么）

| 维度 | 对方报告 | 我们的系统 |
|---|---|---|
| 支付形态 | **在线支付 API 闭环**（预下单→回调→查单→对账） | **收银台组合支付**（现金/微信/支付宝/银行卡/储值余额/分红/积分/赊账 八通道） |
| 微信/支付宝现状 | 已按商户 API 设计 | **记账式**：店员收款码收款后录入金额+流水号（`sale_payments.external_no`），未接商户 API |
| 核心风险域 | 线上假支付/空支付/丢单 | 会员资产漏洞（薅分红、微额刷单）、账实分离、离线幂等 |
| 部署形态 | 通用（SQLite 视角） | 本地部署 + 云端接入层转发回调（6.4.1 已设计） |
| 资金流 | 单向：顾客→商户 | 多向：消费/充值/退款原路/分红发放（负债核算） |

**结论先行**：对方报告不能替代我们的设计，但应作为我们《支付服务模块》的**强制参照标准**吸收。

## 三、逐项能力对比矩阵

| # | 能力项 | 对方报告 | 我们现状 | 判定 |
|---|---|---|---|---|
| 1 | 金额服务端计算 | ✅ 客户端只传订单标识 | ✅ 明细价格取库、促销/券/抹零服务端重算 | 打平 |
| 2 | 支付合计==应收校验 | ✅（金额逐分比对） | ✅ `50031 支付合计与应收不一致`（浮点元 r2） | 我们有校验但**精度口径弱**（见 5.2） |
| 3 | 幂等设计 | ✅ CAS + 唯一索引 + 幂等应答 | ✅ 收银端 `clientRef` 离线幂等 + 部分唯一索引；❌ 在线支付状态机无 CAS（未建） | **缺口** |
| 4 | 异步通知验签 | ✅ APIv3 平台证书 + AES-GCM / RSA2 公钥，含防重放时效 | 设计方案有"回调验签"四字，无实施细则 | **缺口（P0）** |
| 5 | 主动查单兜底 | ✅ 延迟队列 15s/60s/5min×6 + 定时扫描 3min PENDING | H5 章节有 30s→5min 梯度轮询设计（未落地代码） | **缺口（P0）** |
| 6 | 支付状态机 | ✅ PENDING/PAID/CLOSED/REFUNDING/REFUNDED/PARTIAL 显式机 | 销售单"已完成"一态到底；在线订单"支付→转正式单"流程有但状态机不显式 | **缺口** |
| 7 | 超时关单 | ✅ time_expire + 主动关单 | 设计方案有"超时未付订单取消"定时任务描述 | 半缺口 |
| 8 | 支付流水审计 | ✅ payment_records（action 维度 + notify 原文留痕） | ✅ sale_payments（含 external_no）+ 资产三流水（余额/分红/积分 flow_id 留痕） | 打平，侧重不同 |
| 9 | 对账 | ✅ API 拉账单 + 三向比对（平台有本地无/本地有平台无/金额差异） | ✅ V4.13 导入式对账：账单有本地无 / 金额差异 / 疑似重复；❌ 无 API 拉取、本地有平台无方向不显式 | 半缺口（P1） |
| 10 | 退款安全 | ✅ 防超退（≤实付−已退 CAS）+ 退款通知幂等 + 权限留痕 | ✅ FIFO 原批次价退款 + 会员资产原路恢复（564 断言覆盖退款）；退款通知幂等随 API 层未建 | 我们更深，需补 API 侧 |
| 11 | 被扫（扫码枪扫顾客码） | ✅ micropay + 冲正 | 未设计 | 可选 |
| 12 | 沙箱/测试隔离 | ✅ 专章 | 设计方案无支付沙箱章节 | **缺口（P1）** |
| 13 | 组合支付/会员资产 | ❌ 完全没有 | ✅ 八通道组合 + 口径B 本金赠送拆分 + 分红抵扣不计有效消费（5.1.16 反薅窟体系） | **我们独有优势** |
| 14 | 离线收银 | ❌ 未提及 | ✅ 断网收银 + clientRef 补传幂等（8.5.1） | **我们独有优势** |
| 15 | 本地部署回调链路 | ❌ 未涉及（默认公网部署） | ✅ 云端接入层转发 + 断连查单兜底已设计 | **我们独有优势** |
| 16 | 赊账/应收/月结 | ❌ 未涉及 | ✅ 信用额度 + 大客户月结对账 | **我们独有优势** |

## 四、查漏补缺：吸收对方报告的 12 项缺口（按优先级）

### P0 —— 接通商户支付 API 时没有就会亏钱（建 pay_service 模块时强制吸收）

| # | 缺口 | 对方方案要点 | 落地建议（落点） |
|---|---|---|---|
| 4.1 | **通知验签实施细则** | 微信用平台证书公钥（按 Wechatpay-Serial 定位，不是商户证书）+ Timestamp 5 分钟防重放；支付宝用**支付宝公钥**（非自己上传的应用公钥）RSA2 字典序验签 + 1 分钟时效 | 写入设计方案支付服务章节；SDK 选 `wechatpayv3` / `alipay-sdk`，验签封装进 adapter 不裸写 |
| 4.2 | **金额逐分比对** | 通知金额 == 本地订单应付金额，逐分比对；不一致拒绝+告警+不更新订单 | settle 函数校验 `paid_amount !== order.payable_amount`；**金额边界统一转整数分** |
| 4.3 | **CAS 状态机** | `UPDATE ... WHERE status='PENDING'` 检查 rowcount；PENDING→PAID 是唯一收钱迁移 | 新增 `sales_orders.pay_status` 字段族 + CAS SQL；与现有 status（已完成）解耦 |
| 4.4 | **应答格式** | 微信 200+空 body（连换行都不行）；支付宝纯文本 `success`；失败返回失败让平台重试——处理失败却返回成功=假成功 | NotifyHandler 单独封装，不与业务路由混用 |
| 4.5 | **查单兜底** | 延迟查单（15s/60s/5min×6）+ 定时扫超时 PENDING；查单复用通知同一 settle 函数 | 我方 H5 章节已有 30s→5min 设计，统一升级为对方的双通道方案 |
| 4.6 | **预下单幂等** | 同一 out_trade_no 重复预下单返回同一二维码，防一码多单/重复支付 | 预下单前查订单支付状态；`time_expire` 15 分钟 + 超时主动关单 |

### P1 —— 上线前必须补齐

| # | 缺口 | 要点 |
|---|---|---|
| 4.7 | **金额整数分运算** | 我方全链路浮点元 + r2()；支付通道边界必须 `Math.round(元×100)` 转分，杜绝 0.1+0.2 类精度错账。建议新支付模块内强制整数分，商品层维持元+r2 |
| 4.8 | **对账升级为 API 拉取 + 三向比对** | V4.13 导入式对账保留（人工兜底通道），新增每日自动拉微信/支付宝账单；补"本地已收、平台无"显式差异报告（当前只从账单方向匹配，反方向不显式） |
| 4.9 | **沙箱与生产隔离** | 支付宝沙箱 / 微信测试商户号跑通 13 项测试后再切生产；联调库（54329）永不配生产密钥 |
| 4.10 | **密钥管理** | 密钥只存环境变量/600 权限文件；不进 Git（`barcode.lookup.mxnzp` 凭据已用 system_settings 的模式可复用，但支付密钥敏感级更高，须独立） |

### P2 —— 增强项

| # | 缺口 | 要点 |
|---|---|---|
| 4.11 | **被扫（扫码枪扫顾客付款码）** | 称重台/快速通道场景：micropay 金额确认 UI + 防重复扫（5 秒禁扫窗）+ 冲正流程。2D 面阵扫码枪硬件本就具备 |
| 4.12 | **通知原文留痕** | `last_notify_raw` + notify_times 计数，纠纷时可回放；我方 sale_payments 可加 `raw_notify JSONB` |

## 五、对方报告照出的我方三个自查风险

1. **"记账式收款"本身是最强防线也是最大天花板**：店员见钱到账才确认，天然免疫假支付——但也意味着高峰期靠人眼核对到账金额，且无法自动出票闭环。**建议过渡方案**：店员扫顾客付款码记账时，要求录入 external_no 并与 POS 屏显应收逐位核对（现有 UI 已支持），接 API 前先加"金额二次确认弹窗"。
2. **浮点元全链路**：现有 r2() 双重舍入在两三位小数内实践安全，但支付 API 层引入后（金额跨系统传输）必须整数分化（见 4.7）。
3. **在线订单支付状态机不显式**：设计方案 8.x 在线订单流程有"支付→转正式销售单"，但无显式状态字段与 CAS。接支付 API 时一并补（4.3/4.6）。

## 六、我们已有、对方报告未覆盖的防线（保持并发扬）

| 防线 | 说明 | 对方盲区原因 |
|---|---|---|
| 会员资产账户体系 | 余额/分红/积分服务端扣减 + 三套流水留痕 + 口径B 本金赠送拆分 | 对方无会员储值业务 |
| 有效消费反薅窟体系（5.1.16） | 分红支付不计有效消费、单笔≥5 元、窗口累计≥50 元、终身封顶 30% | 纯商品收银不涉及分红合规 |
| 离线收银幂等（8.5.1） | clientRef + 部分唯一索引，断网补传不重账 | 对方默认在线 |
| FIFO 批次退款 | 按原批次价退、多供应商分批独立、会员资产原路恢复 | 对方退款只到"金额≤实付"粒度 |
| 本地部署回调架构 | 云端接入层转发 + 断连查单（6.4.1 已设计，对方默认公网部署） | 对方未考虑本地化部署 |
| 赊账/应收/月结 | 信用额度锁定开单、大客户月结对账 | 对方纯即时支付 |

## 七、行动路线建议（三步走）

1. **现在（不接 API 也能做）**：支付模块代码内预先统一"整数分"边界函数；给记账式收款加金额二次确认；对账补"本地有平台无"报告（P1-4.8 的反方向，纯本地可做）。
2. **接 API 时（开店线上业务/会员充值前）**：按对方报告 04/05/07 章建 `pay.service`（WechatAdapter/AlipayAdapter/NotifyHandler/QueryJob），P0 六项逐条验收；对账任务升级为 API 拉取。
3. **上线时**：跑对方 13 项测试清单 + 上线 Checklist（密钥隔离、0.01 元真实支付→退款全链路验证）；生产回调走云端接入层，断连演练一次查单兜底。
