〇、总体结论（先说重点）

这份方案的主体能力，当前系统里大部分已经落地——15 项能力中 9 项已实现、4 项部分实现（MVP 级），真正未做的只有 3 项（漏扫检测、语音交互、智能客服），且方案自己把它们排在 Phase 2–3。

两份方案的哲学高度一致："规则引擎 + 统计基线给建议，决策权在人，数据不出店"。现有系统的 aibrain.engine.ts（智能决策中心） + ai.pricing / ai.market / coupons / promotions / marketing / inventory 模块群，就是方案 03/04/05 章的实现载体。

下一步真正值得投入的只有 2 件事：① 漏扫检测 MVP（支撑自助收银可信化）；② 支付平台账单导入对账（财务安全闭环）。其余按性价比见第三章。

一、逐项详细分析

01 感知层

1.1 商品识别 —— ✅ 已实现，且实际架构优于方案稿

  • 方案稿写的是 YOLOv8s + CLIP ViT-B/32 + FAISS（早期口径）；现系统已迭代到 Chinese-CLIP ViT-B/16（量化 ONNX，进程内推理）+ JSONB 向量应用层余弦 + 中文商品名 rerank + 零训练轮廓分割多件识别 + 电子秤 + 别名表（V4.10.1→V4.11.4）。
  • 方案的"条码精确兜底优先于外观""VL 语义兜底（qwen2.5vl:3b）""规格 OCR"三设计全部与现系统一致（条码双引擎 BarcodeDetector+zxing-wasm / Ollama 兜底 / ai.ocr.ts）。
结论：不需要动。方案文档技术栈表建议按 v3.2 口径更新（FAISS→JSONB 余弦足够、SQLite→PG 已更强）

1.2 防损 / 漏扫检测 —— 🟡 拆两半看，漏扫检测是本次最值得引进项

  • 损耗预警侧：已实现。aibrain"防损基线"（批次剩余效期扫描 → 8 折去化/退供建议）、inventory expiry-alerts + 效期报损处置流程（expiry-disposals/:batchId/start|done）、ai.pricing 临期折价，三处已闭环。
  • 漏扫检测侧：未实现。方案 MVP（结算一致性校验：识别件数 vs 结算件数 + 理论重量 vs 实秤重量）成本极低且数据条件已备齐——识别管线返回逐件 count，电子秤读重已接入 checkout（V4.11.2）。自助收银（member-app self-checkout）没有这道校验等于裸奔。
  • 进阶行为识别（姿态/手部关键点）：缓做，单店人力监控可比，标注成本高，方案也只给了 -50% 盗损的公开报道口径，先验证 MVP。
结论：可引进，优先级最高（详见第三章）

1.3 会员识别 —— ✅ 已实现

会员码/手机号 + member-app（注册/登录/流水/消费）+ 收银端挂接会员，与方案"推荐简版"完全一致；刷脸方案自己也标了"谨慎"，不做。

结论：不需要动

1.4 货架 / 陈列感知 —— ⏸ 可扩展

识别管线可 100% 复用（手机拍照 → CLIP → 商品），技术上是现成积木；但"缺货空位/错位"需要货架基准照比对逻辑，属新开发。建议排在自助收银防损之后，或先以"巡店拍照建档样本"的形式顺带积累素材。

结论：扩展项，Phase 3

02 交互层

2.1 语音收银 —— ⏸ 可扩展，建议只做单点

whisper.cpp + piper 全链路本地可商用，技术无障碍；但对店员收银场景，扫码枪+触屏已比说话快且准，语音价值在"口头查价/双手占用时"。建议 Phase 3 先做「语音查价」单点（ASR→意图[查价]→报价 TTS），验证店员是否真用，再谈语音下单。

结论：扩展项，先做语音查价单点验证

2.2 自然语言报表 —— 🟡 MVP 已实现

aibrain qa 端点已有：日报全文检索 + 关键词匹配降级 + ai.llm.enabled 可选 LLM 底座 + 日报摘要（"老板能看懂的话"）。方案 MVP 路线（SQL 查数 + LLM 组织语言）与现状同构。改进项：把"今日毛利/畅销榜/损耗榜/库存预警"等高频问题做成预置问题按钮（一天工作量）；NL2SQL 缓行——幻觉与注入风险对财务数据不值当，方案的约束清单（白名单+只读+上限）真要做也别早于 Phase 3。

结论：MVP 已实现；改进 = 预置问题按钮

2.3 智能客服 —— ⏸ 扩展，最低优先

会员 H5 已有自助查询（订单/流水/价格），售后问题在小店场景用"老板微信"解决效率更高。若做，FAQ 向量检索可复用现有文本嵌入能力（ai_name_embs 同款 Chinese-CLIP 文本塔），开发量不大但价值密度低，放最后。

结论：扩展项，最低优先

03 决策层（方案要求数据门槛：≥8–12 周真实流水）

3.1 销量预测 —— 🟡 规则级已实现，模型升级看数据

aibrain 已有"销售预测"应用（统计基线）。方案的 Prophet+LightGBM 混合是数据攒够后的自然升级，不是现在欠的账：单店日几百单，8–12 周前上 LightGBM 是过拟合机器。结论：保留现状，开业满一季度后用真实流水回测基线准确率，再决定是否引入 LightGBM（现栈 Node 侧可走 onnx/PMML 或独立 Python 服务，届时再评估）。

结论：保留现状，数据门槛未到不升级

3.2 智能补货 —— ✅ 已实现

aibrain restock：安全库存法 + 在途扣减（order_qty − arrived_qty）+ 覆盖天数/安全天数设置键（ai.restock.coverage_days / safety_days），与方案公式同源（补货点=日均×提前期+安全库存）。建议一律"待处理→人工执行/否决"，否决留痕作训练信号。不需要动；开业后可加"供应商维度合并建议单"作为增强。

结论：不需要动

3.3 AI 选品 —— 🟡 部分实现

已有：购物篮关联分析（aibrain）、ABC 分类报表（boss repAbc）、动销数据。缺口：方案口径的"淘汰/上架建议"输出（动销率<阈值且周转慢→建议淘汰清单）。这是在现有数据上加一个 aibrain domain + 一张建议卡片的量。结论：改进项，可做。

结论：改进项，可做（小工作量）

3.4 临期动态定价 —— ✅ 已实现，且比方案细

ai.pricing：临期（≤7 天 5 折 / ≤15 天 7 折 / 其余 8.5 折）+ 滞销（60 天无销售且库 ≥30 件） + 成本底线（建议价 ≥ 进价 ×1.05）——方案只有临期档位，现系统多了滞销与保本约束，且与调价单流程打通。不需要动。

结论：不需要动（比方案更细）

3.5 会员个性化营销 —— ✅ 已实现，超方案

  • ai.market：按画像生成定向方案（沉睡唤醒/高价值回馈/偏好品类满减）→ 执行写 marketing_touches → 效果回测（触达前后消费对比）；
  • coupons：满减/折扣/兑换/次卡四类券，核销留痕进订单记账口径；
  • promotions：商品级/分类级/整单级三层促销引擎（同层取优、跨层叠加可配）；
  • marketing.module：定时引擎（生日触达/临期折扣/分红到期提醒，每分钟检查+补跑）。
结论：方案这一节基本是给现有系统做注脚，不需要动；RFM 显式三字段可作为画像表小增强

04 运营层

4.1 自助收银 —— 🟡 雏形已有，补防损即可转正

member-app self-checkout 接口存在。要达到方案"高峰辅助/低峰无人值守"的可用状态，缺的是 1.2 的漏扫校验 + 异常告警（差异即暂停待店员复核）。结论：改进项，与漏扫检测打包做。

结论：改进项，与漏扫检测打包做

4.2 自动对账 / 日结 —— 🟡 半实现，账单导入对账可引进

  • 已有：班次交接对账（移动收银自动挂班次、recon 补签场景）、AI 日报 23:59 自动生成含对账要素。
  • 缺口：支付平台账单（微信/支付宝导出 CSV）与本地流水的自动对齐。这是财务安全的最后一块，纯规则解析无需 AI。结论：可引进，开业后第一优先（真实收款渠道确定后做，避免空转）。
结论：可引进，开业后第一优先

4.3 自动报表 —— ✅ 已实现

AI 日报（当日全指标+异常事件+知识库归档，23:59 自动）+ boss 端营业日报/ABC/商品明细/会员榜/进销存/员工业绩/AI 识别质量七类报表，手机 H5 直达。方案"识别质量报告驱动补拍照片"也已在 M4 闭环中。不需要动；可加日报定时推送（微信/邮件）作为增强。

结论：不需要动

4.4 效期管理 —— ✅ 已实现

建档录保质期 → 批次 expiry_date → expiry-alerts 临期预警 → 效期报损处置流程 → ai.pricing 临期折价联动，与方案 4.4+3.4 联动设计一致。不需要动。

结论：不需要动

05 资产层

5.1 顾客画像 —— ✅ 已实现（够用）

画像分层已在 ai.market 中驱动营销（沉睡/高价值/偏好品类）。方案的"≥12 维标签实时优惠"对小店是过度工程，方案自己在风险清单里也承认数据量天花板。不需要动；R/F/M 显式三字段可作为小增强。

结论：不需要动

5.2 统一数据底座 —— ✅ 已实现，且强于方案

方案核心表清单（products / stock_movements / orders / recognize_logs / members / price_rules / forecast_results）在现系统全部有对应物且更完整（FIFO 批次表、batches、ai_suggestions、marketing_touches、ai_recognition_logs 含 layer/corrected）。PostgreSQL + 流水累计可对账 + 单据经手人可审计，方案的两条铁律本就是现系统的设计底线。不需要动。

结论：不需要动

5.3 模型自进化 —— ✅ 识别侧已完整实现

识别侧：人工修正写回识别日志 → 纠正帧进样本库 → 审核通过自动重建向量 → 质量报表驱动补拍闭环（V4.11.3–V4.11.5 刚补完三缺口）。预测侧：规则引擎天然"每次重算"，无需 MLflow。已达标；若未来引入 LightGBM 再考虑实验跟踪。

结论：已达标

三、行动建议（按性价比排序）

#事项对应方案工作量理由
1 漏扫检测 MVP：自助收银结算一致性校验（识别件数 vs 结算件数）+ 称重商品理论重 vs 实秤校验，差异即暂停复核 1.2 MVP + 4.1 小（数据与组件全现成） 自助收银可信化的前提；防损收益直接
2 支付账单导入对账：微信/支付宝 CSV 导入 → 按金额+时间对齐 → 差异清单 → 日结对账单 4.2 中（规则解析） 财务安全闭环；开业收到真实账单即可启动
3 AI 选品建议：动销/周转四维打分 → 淘汰/上架建议单进 aibrain 待处理建议流 3.3 小 纯增量，复用建议-确认-留痕机制
4 qa 预置问题：今日毛利/畅销榜/损耗榜/库存预警做成一键按钮 + LLM 摘要开关调优 2.2 很小 老板端体验立竿见影
5 货架巡店（Phase 3）：手机拍照 → CLIP → 空位/错位标记，先从"巡店拍照顺带积累样本"切入 1.4 中 识别管线 100% 复用，等稳定运营后做
6 语音查价单点（Phase 3）：whisper.cpp + 意图规则 + piper 报价 2.1 中 先验证店员真用，再谈语音下单
7 预测升级 LightGBM（开业满一季度、流水 ≥8–12 周后回测再定） 3.1 大 数据门槛未到，现在做是空转

明确没必要做的：刷脸会员识别（合规+方案自不建议）、12 维画像实时优惠（数据量天花板）、大模型实时动态定价（方案已否）、行为识别进阶（先跑 MVP 一致性校验）、FAISS/SQLite/YOLO 重构（现有实现更优或不划算）。

四、与方案落地节奏的对齐

  • Phase 1（方案：0–2 月）：现系统已整体超额完成（识别/流水/报表/手机端/自助雏形/会员码全在），方案 Phase 1 验收口径（单件 1 秒内、准确率>95%、日结对账跑通）中前两条已达成，第三条差"账单导入对账"（行动 #2）。
  • Phase 2（3–6 月）：数据门槛 ≥8–12 周流水——主体能力（补货/定价/营销/效期/画像）已提前建成，开业后重点是"用起来 + 回测建议命中率"，而非新开发。
  • Phase 3（远期）：语音/NL 报表进阶/行为识别/巡店/客服，按本报告第三章排序逐项评估。

一句话总结：这份能力全景可以当作现系统的"验收对照表"——真正的增量开发集中在自助收银防损和账单对账两处，其余是"用数据喂熟已有能力"的运营功课。
