R-NEW-1 · 测试基建三连断：干净环境 e2e 完全无法运行（门禁整体失效）

三个独立断点叠加：① 迁移 197 注释自称幂等但 REVOKE ... FROM pos_app 在角色不存在的干净集群直接报错（部署路径靠 server-up.mjs 先建角色掩盖）；② e2e 只 pipe 服务子进程 stderr，stdout 无人消费 → 64KB 缓冲写满阻塞子进程，服务永不就绪；③ V4.24.0 起管理员改为 bootstrap 引导创建，e2e 仍以写死的 ADMIN/出厂默认密码登录 → 41001，且 P0-F3 断言依赖的 LEGACY_DEFAULT_PW env 未传。
验收修复（3 处）：197 包 DO $$ IF EXISTS(pg_roles...) $$；e2e 补 server.stdout.on('data',()=>{})、bootstrap-admin 调用与 LEGACY_DEFAULT_PW 注入。教训：这正是「无 CI」的代价——修复 PR 没有任何门禁能发现干净环境被炸。
P1已修复（验收中）

R-NEW-2 · L-09 回冲与退款基数/满额判定冲突：第二笔部分退款恒算 0 被拒（少退/拒退）

L-09 修复把 payable_amount 变为动态净额，但退款链四处仍按「原始总额」语义使用它：calcRefundRows 基数 净应付 − Σ已退(含已回冲) 双扣 → 首笔部分退款后，后续退款金额恒 0（40003 拒退，e2e S4 实证）；refundRatio 分母缩小 → 积分/分红冲回偏多；otherAmt 双计；满额判定 refundedSum ≥ 净应付 在部分回冲后恒真 → 首笔部分退款即被误置「已退款」（e2e S5 实证，订单无法继续退款）。
验收修复（refund.module.ts 5 处）：基数只扣未回冲（待审核/创建中）；比例分母改用 净应付 + 已回冲累计（原始成交额）；otherAmt 只计未回冲；满额判定改 payableCents <= 0 且 CAS 分支同步。建议：为 sales_orders 增加原始 payable 快照列，终结「动态净额 + 多处语义混用」的结构性风险（V-50b 对账哨兵可拦截复发）。
P1已修复（验收中）

R-NEW-3 · 挂单恢复结账被改价授权闸误伤：含改价行的挂单永久 50035

needsPriceAuth 强制整改后，/pos/held/:id/checkout 从快照恢复的行天然带 unitPrice → 命中「改价需店长授权」→ 且该端点 DTO 没有 priceAuthTicket 字段、也不透传 → 含改价行的挂单永远无法结账（e2e R10 实证 50035）。硬拒行为本身正确、通道缺失是缺陷。
验收修复（pos.module.ts 2 处）：DTO 增加 priceAuthTicket 并透传给 sales.checkout（e2e R10 补票后全绿）。产品确认项：挂单快照价 = 挂单时已生效价格，是否应豁免授权（建议：快照价 == 档案价时豁免，仅真实改价要求票据）。
P1已修复（验收中）

R-NEW-5 · 停用/复职接口 SQL 参数类型冲突（S-01 修复自身崩溃）

SET status=$2 ... CASE WHEN $2='停用' 同参双用途 → PG inconsistent types deduced for parameter $2 → 停用/复职接口 50000（e2e T 段实证）。首轮补显式转型时注释误入 SQL 模板又引发第二处语法错，均已修正。
验收修复：改用列引用 CASE WHEN status='停用'（SET 后新值），彻底消除第二个参数占位。

本次新增「整单应收 < max(最低卖价线, 进价) 需店长授权」把 会员价 1.2 元、特价 0.1/1.5 元等场景一并拦截（e2e K6/K7 实证 50038）。红线防「叠加优惠击穿」的意图正确，但会员价属长期定价而非临时叠加。e2e 已按贴线价校正（语义保留：会员价 < 特价 → 取会员价）。待产品拍板：会员价是否豁免红线（若是，pricing 红线计算需按「非会员价基准」重算）。

R-NEW-6 · 负库存软模式失效：stock.negative_sales=true 时缺货结账仍被 50001 硬拒

动态取证（pricing 探针）显示 allowNeg=true 在 pricing 闸已正确放行，硬拒出自 persist 落账端——根因：persist 批量化改造时给 batchInv 加的 done 硬检，把「软模式下库存行不存在（从未入库）→ UPDATE 命中 0 行」误判为失败（旧实现静默放行）。影响：软模式整体失效，收银台无法对缺货商品做「先卖后补录成本」操作。
验收修复（persist.ts）：batchInv 拆分——软模式行走 UPSERT（无行插负余行，与 L-18 盘盈对称），硬模式行保留原子校验 + done 硬检。SN 三项断言转绿，e2e 664/664。
