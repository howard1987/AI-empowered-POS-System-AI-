一、缺陷清单 4 项（1 已修复 / 3 待修复）+ 1 项观察

已修复D1 · 审计序列错位致全站无法登录P0 · 数据态已校准，建议产品化加固
现象
任意登录请求返回 40009 已存在重复记录（audit_logs_pkey），门店无法登录、全部业务停摆。
证据
max(id)=31003171 而 audit_logs_id_seq.last_value=31003170（序列落后 1），下一次 nextval() 撞已存在主键；服务端 logs/error.log 命中 duplicate key ... audit_logs_pkey（调用栈 audit()→AuthService.login）。
根因
存在以显式 id 写入审计表的路径（备份恢复 / 批量导入），恢复后未校准序列。
现状
已执行 SELECT setval('audit_logs_id_seq',(SELECT max(id) FROM audit_logs)) 恢复；复测 max_id = seq_last_value = 31003381，当前健康。
建议
恢复/导入后统一对全部序列 setval 校准；并让审计写入失败不阻断主业务（降级为告警）。
待修复D2 · POS 日报接口 500（sale_refunds 无 pay_paid_at 列）P1 · 用例 D2
现象
GET /pos/daily?date=YYYY-MM-DD 恒返回 500「系统错误」，POS 日报完全不可用。
证据
服务端日志：column r.pay_paid_at does not exist（调用栈 q1()→PosController.daily）。源码 backend/src/modules/pos.module.ts:687 退货子查询写作 COALESCE(r.pay_paid_at, r.created_at)，而 sale_refunds（别名 r）实际 26 列中不含 pay_paid_at（information_schema 已核）。
影响
门店日报/交班对账不可用，属日常高频功能。
建议
改为 r.created_at（退货按退款时刻归属），或为 sale_refunds 增列 pay_paid_at 并回填 =created_at 后统一口径。
[2026-10-09T01:51:37.597Z] [filter] error: column r.pay_paid_at does not exist at pg-pool → q1 (dist/common/db.js:56) at async PosController.daily (dist/modules/pos.module.js:637)
待修复D3 · 备份恢复演练失败（恢复以非属主角色执行）P1 · 用例 67b
现象
「系统设置→应急与运维→恢复」执行即失败，灾备链路不可用。
证据
历史错误 must be owner of table sync_nodes；本机复核：public 下 155 张表全部属主为 postgres，而业务进程以最小权限角色 pos_app（非超户、非属主）运行——pg_stat_activity 实测后端 6 条连接身份均为 pos_app。admin.backup.ts:230 恢复命令为 pg_restore --clean --if-exists --no-owner --dbname DATABASE_URL，--clean 需 DROP 属主对象，权限不足即中断（--no-owner 不能豁免 DROP 的属主校验）。
影响
真正需要灾备时无法恢复，属上线关键风险。
建议
恢复链路改用属主/超户连接串（如独立的 RESTORE_DATABASE_URL）；或将 --clean 失败显式回传前端，避免「静默半恢复」。
public 表属主统计：postgres = 155 张（100%） 后端连接身份（pg_stat_activity）：pos_app × 6 ← 恢复所用角色 pos_app: rolsuper=false rolcreatedb=false rolcreaterole=false 恢复命令：pg_restore --clean --if-exists --no-owner --dbname $DATABASE_URL → must be owner of table sync_nodes
待修复D4 · 并发超卖 / 负库存（间歇，双库存台账口径不一致）P1 · 用例 12
现象
高并发抢购同一商品时，库存台账 inventory_current.qty_total 可被扣成负数。
证据
实测捕获 1 次：库存 65.53 → −0.47，5 并发（每单 33 件）中 2 单成功，合计扣减 66 > 现有 65.53。
根因
超卖闸读的是批次可用量 Σ batches.remain_qty（sales.module.ts:364-375，带 FOR UPDATE），而落账写的是另一本账 inventory_current.qty_total（sales.module.ts:700），两本账彼此独立、可漂移，且台账行未加锁、未复核。全店扫描已证明两账会不一致（如 pid 120：台账 17 / 批次 16.235；pid 75：台账 4 / 批次 2）。当某商品批次可用量 > 台账时，闸门放行而台账扣穿 → 负库存。
复现性
属间歇性竞态：补充压测（12 轮 × 5 并发）未再次触发，说明与两账漂移方向/时序强相关，非稳定逻辑错误——但风险真实存在。
建议
① 统一库存权威口径（超卖闸改读 inventory_current，或在同事务内 SELECT ... FOR UPDATE 锁台账行并以其为唯一判据）；② 落账用 UPDATE ... WHERE qty_total >= $x 原子扣减并校验影响行数；③ 增加两账一致性巡检/对账任务。
实测：库存 65.53 → −0.47 成功 2/5（每单 33 件） 全店两账漂移扫描（inventory_current − Σbatches.remain_qty）： pid 120 V4132通道测试品 台账 17 批次 16.235 漂移 +0.765 pid 75 益达无糖口香糖 台账 4 批次 2 漂移 +2 → 闸门(批次) 与 台账(inventory_current) 为两本独立账，漂移方向可正可负
观察项O1 · 幂等兜底触发时错误日志噪音P2 · 建议优化

双击/并发重复结账时命中 ux_sales_client_ref 部分唯一索引，服务端以 [filter] error 级别记录 duplicate key ... ux_sales_client_ref。

四、验收口径与说明

验收口径：资金零差错（Σ渠道实收 = Σ应收）｜单据不重不漏（订单号唯一、离线补传幂等）｜库存不为负｜金额精度零误差（分/角/分）｜权限与留痕完整｜硬件异常不影响账务。
测试方法：全量自动化执行器 qa-all68.mjs 覆盖 P1–P8，共 70 条记录（自动断言 48 + 人工 18 + 跳过 4），直连运行中的服务并经只读 SQL 核对 PostgreSQL；另有 qa-manual18.mjs 对 6 项可纯后端验证的用例（17/42/53/55/59/63）做 API 断言，均通过（结论列标记为「已验证」）。 缺陷 D1/D2/D3/D4 均给出可复现证据链（服务端日志、源码行号、information_schema、pg_stat_activity、两账漂移扫描）。
数据说明：为不影响真实账务，测试均使用可回收测试商品并走应用层入库补货；破坏性恢复演练（67b）未实际执行，仅做根因取证； 测试后已还原被改动的系统设置项。
上线建议：先修复 D2、D3、D4 并复测（D4 需专项并发回归 + 两账对账），再补做 18 项人工实机验证，方可进入上线评审。
